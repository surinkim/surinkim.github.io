### [GitHub Actions 모니터링의 빈칸: Exporter로 ARC Runner 관측하기](https://medium.com/daangn/github-actions-%EB%AA%A8%EB%8B%88%ED%84%B0%EB%A7%81%EC%9D%98-%EB%B9%88%EC%B9%B8-exporter%EB%A1%9C-arc-runner-%EA%B4%80%EC%B8%A1%ED%95%98%EA%B8%B0-cbe1a46a9e71)

당근 SRE팀이 쿠버네티스에서 self-hosted Runner를 관리하는 ARC(Actions Runner Controller)를 운영하며 "Job이 Queued에서 안 넘어가요" 문의에 답하려고 exporter를 직접 만든 글입니다. Collector는 EphemeralRunner와 Runner Pod 이름이 같다는 점을 이용해 Pod에 저장소·Job 이름 라벨을 붙이고, Webhook은 `workflow_job` 이벤트로 대기 중인 Job 수와 대기 시간 히스토그램을 내보냅니다. 대기 시간 대신 Job 생성 시각을 값으로 두고 `time() - 메트릭`으로 계산하게 한 것, 순서가 뒤바뀌어 도착하는 웹훅을 상태가 앞으로만 진행한다는 전제와 완료 표시(tombstone)로 처리한 것이 따라 해 볼 만한 설계입니다. 후반부의 장애 회고도 좋습니다. 모든 데이터를 TTL 6시간 하나로 관리하다 스냅샷이 8MiB 상한을 넘어 저장이 멈췄고, OOM으로 재시작한 Pod가 2시간 44분 전 스냅샷을 복원해 이미 끝난 Job을 대기 중으로 72개나 알렸습니다. 데이터 종류별로 보관 기간을 나누고(스냅샷 크기 8MiB → 0.66MiB), 실패한 웹훅 재전송과 GitHub API 대조(reconcile)를 붙여 해결했습니다.

관련: [영문판](https://medium.com/daangn/closing-the-github-actions-monitoring-gap-observing-arc-runners-with-an-exporter-0a8f39c3b70b)

### [When a sync window closes: How Argo CD self-heal skipped the migration hook](https://www.cncf.io/blog/2026/11/20/when-a-sync-window-closes-how-argo-cd-self-heal-skipped-the-migration-hook/) (sync window가 닫힐 때 Argo CD self-heal이 마이그레이션 훅을 건너뛴 이유)

배포 금지 sync window 중에 릴리스를 올렸더니, 창이 열린 뒤 5개 리전 중 2곳에서 DB 마이그레이션(Sync 훅 Job)이 실행되지 않았습니다. UI는 Synced·Healthy였고, 새 코드는 36~44분 동안 맞지 않는 스키마를 상대했습니다. 원인은 경쟁 상태(race)입니다. 창이 닫힌 뒤 주기적 비교(level-2 refresh)가 먼저 오면 정상적인 전체 sync가 돌지만, 리소스 변경으로 생긴 refresh(level-1)가 먼저 오면 마지막으로 "비교한" 리비전을 마지막으로 "sync한" 리비전으로 착각해 self-heal의 부분 sync로 처리하고, 부분 sync는 훅을 하나도 실행하지 않습니다. 작성자는 실습 환경에서 6번 중 5번 재현했고, 훅을 PreSync로 바꾸거나 `RunHooksOnPartialSync`를 켜도 소용없다고 설명합니다. 해법은 마이그레이션을 훅이 아니라 원하는 상태의 일부로 만드는 것입니다. 릴리스마다 이름이 바뀌는 Job에 sync-wave `-1`을 주면 어떤 종류의 sync든 없는 리소스로 보고 먼저 적용합니다.

### [How we scaled metrics aggregation by moving durable state into storage](https://www.datadoghq.com/blog/engineering/how-we-scaled-metrics-aggregation/) (지속 상태를 스토리지로 옮겨 메트릭 집계를 확장한 방법)

Datadog이 태그 차원을 줄여 메트릭을 합치는 집계 서비스를 세 세대에 걸쳐 다시 설계한 이야기입니다. 늦게 도착하거나 중복된 데이터를 바르게 반영하려면 집계 서비스가 상태를 들고 있어야 하는데, 이 상태 관리가 확장의 병목이 됐습니다. 1세대는 Kafka 파티션을 노드에 고정하고 RocksDB에 몇 시간치 상태를 두는 리더·팔로워 구조였습니다. 계산이 두 배로 들고, 파티션 하나를 나누는 데 1.5시간짜리 수작업이 필요했습니다. 2세대는 파티션을 동적으로 재배정하고 RocksDB 증분 스냅샷을 blob 스토리지에 올려, 최근 시간 창부터 복원하는 방식으로 약 10배 물량을 감당했습니다. 3세대는 스트리밍 계층의 집계·중복 제거를 최선 노력(best-effort)으로 낮추고, 부분 집계 형식을 스토리지가 이해해 늦은 데이터와 중복을 스토리지에서 맞추게 했습니다. 그래서 재시작한 노드가 몇 시간치 상태를 복원하지 않고 바로 최신 데이터부터 처리할 수 있게 됐습니다. Kafka 뒤에 상태를 가진 처리기를 두는 구조라면 "정확성의 책임을 어디에 둘지"를 생각해 보게 하는 글입니다.

### [지표 뒤에 숨은 맥락을 한눈에: New20 Timeline Hub 만들기](https://toss.tech/article/new20-timeline-hub)

토스에서 "그날 제품에서 무슨 일이 있었나요?"라는 질문에 답하려고 만든 타임라인 도구입니다. 배포 채널, PR, 회의록, 정책 문서에 흩어진 기록을 정책·혜택, 세그먼트, 노출 지면, 실험, 데이터·대시보드 다섯 갈래로 나눠 하나의 시간축에 올렸습니다. 개발 반영이 확인된 변경은 채운 점, 논의만 있는 항목은 빈 점으로 구분했고, 여러 PR과 회의록을 한 변경으로 묶되 근거 원문을 함께 연결했습니다. 노트를 저장한 날과 실제 결정한 날을 구분한 것, "여기 없으니 없던 일"로 읽지 않도록 수집하지 못하는 범위를 화면에 밝힌 것은 장애 분석용 변경 타임라인을 만들 때도 그대로 쓸 수 있는 원칙입니다. 작성자는 시점이 겹친다고 원인이 증명되지는 않으며, 타임라인은 검증할 가설을 찾는 출발점이라고 강조합니다.

### [Using a "chaos loop" to harden the Claude Docs launch](https://claude.dev/blog/chaos-loop-claude-docs-launch/) (chaos loop로 Claude Docs 출시를 단단하게 만든 방법)

Anthropic이 문서 편집기 Claude Docs를 출시하기 2주 전부터, Claude Code 세션 하나가 스테이징 클러스터에 하루 100만 개 넘는 가상 문서를 밀어 넣고 일부러 부수는 루프를 계속 돌렸습니다. 시나리오를 고르고, 부하를 걸고, Datadog MCP로 텔레메트리를 읽고, 수정안을 내고, 되돌리기 쉬운 변경은 직접 스테이징에 배포해 다시 돌리는 식입니다. 스키마 변경처럼 되돌리기 어려운 결정만 사람이 승인했습니다. 텔레메트리를 Claude가 읽기 쉽게 만든 점이 핵심입니다. 모든 DB 쿼리가 이름과 스캔한 행 수 대비 반환한 행 수를 남기게 했고, 측정한 숫자가 직접 짠 코드로 바로 이어지도록 GC가 없는 Rust로 작성하고 의존성을 최소로 줄였습니다. 그 결과 큰 문서 하나가 3GB를 쓰던 원인(키 입력마다 문서를 여러 자료 구조에 복사)을 찾아 copy-on-write로 바꿔 180MB로 줄였고, 출시에 필요한 파드 추정치가 500개 이상에서 약 50개로 내려갔습니다. 출시(9월 16일) 후 9월 22일까지 문서가 460만 개 넘게 만들어졌고, 요청 20억 건에서 서버 오류는 60건이었으며, 연습한 시나리오 10개 중 7개가 실제로 일어났습니다. 추론 비용은 약 $125,000였다고 밝혔습니다.

### [How the Claude Code team thinks about verification](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/) (Claude Code 팀이 검증을 바라보는 방식)

코드의 약 90%를 Claude가 쓰고 리뷰하는 Claude Code 팀이 에이전트에게 "증거로 검증하게" 하는 방법을 정리한 글입니다. 투자할 만한 테스트로 세 가지를 꼽습니다. 실제 사용자 흐름을 따라가 속이기 어려운 E2E 테스트, "인코딩 후 디코딩하면 원래 값", "잔액은 음수가 될 수 없다", "두 번 실행해도 결과가 같다(멱등성)" 같은 성질을 무작위 입력 수천 개로 깨 보는 속성 테스트(property test), 같은 입력을 옛 시스템과 새 시스템에 넣어 결과를 비교하는 차분 테스트(differential test)입니다. 불안정한(flaky) 테스트는 에이전트에게 "고치지 말고 다시 돌려라"를 가르치고, 느린 테스트는 검증 횟수를 줄인다는 경고도 있습니다. 팀은 앱을 띄우고 조작하는 방법을 `verify` 스킬로 저장소에 두고, Claude가 커밋 전에 이 스킬로 실제 동작을 확인하게 합니다.

### [How OpenAI's Performance Factory keeps ChatGPT fast](https://openai.com/index/how-openai-performance-factory-keeps-chatgpt-fast) (OpenAI의 Performance Factory가 ChatGPT를 빠르게 유지하는 방법)

성능 알림이 울리면 Codex 에이전트가 원인을 조사하고, 수정안을 올리고, 배포 뒤 성능이 기준선으로 돌아왔는지까지 확인하는 시스템입니다. 3개월 남짓 동안 1,700건 넘게 조사했고 600건 넘게 근본 원인을 찾았습니다. 눈여겨볼 부분은 여기까지 온 단계입니다. 사람이 지표와 트레이스를 직접 보던 단계에서, Codex와 함께 조사하는 단계, 성능팀의 조사 절차(언제 느려졌나, 어떤 요청인가, 배포·설정 변경 때문인가)를 `perf-forensics` 스킬로 정리하고 과거 회귀 사례로 평가(evals)한 단계, 알림을 복사해 붙이던 사람을 자동화로 빼는 단계로 나아갔습니다. 최종 구조는 작업 추적기, 준비된 작업을 에이전트에 배정하는 디스패치 루프, 클라우드 실행 API, 리뷰 코멘트나 배포 완료 같은 이벤트에 에이전트를 깨우는 구독의 네 부분입니다.

### [How Public Evals Work and Fail, and What Should Change](https://eugeneyan.com/writing/public-evals/) (공개 벤치마크는 어떻게 작동하고 어디서 틀리는가)

Eugene Yan이 코딩·과학, 지식 노동, 브라우징·컴퓨터 사용 분야 공개 벤치마크 12개를 뜯어본 글입니다. 평가 과제는 지시문, 실행 환경, 채점기(grader), 선택적인 사람 정답의 네 요소로 이뤄지고, 대부분 LLM 판정보다 코드 기반 검사를, 과정보다 결과를 보는 채점을, 부분 점수 없이 전부 통과해야 하는 방식을 택한다고 정리합니다. 그런데 12개 중 8개에서 맞는 결과를 채점기가 떨어뜨린 흔적이 있었다고 합니다. 모델이 자주 틀리는 방식은 결과를 확인하지 않고 일찍 끝내기와 명시된 요구 사항 빠뜨리기였습니다. 벤치마크 점수를 읽을 때 무엇을 믿고 무엇을 의심할지, 직접 평가 세트를 만들 때 무엇을 피할지 배울 수 있습니다.
